# Як пояснити AlgorithmLab

Почни з `Main`: створення списку, вибір компаратора, виклик merge sort. Далі простеж один `insert` і один `unlink` на папері. Після кожної зміни `head.previous == null`, `tail.next == null`, count відповідає кількості вузлів, а сусідні посилання узгоджені. Індекс `size` допустимий для вставки, але не для читання. Зміна версії робить старі ітератори непридатними; це діагностика, а не захист від потокових гонок.

Selection знаходить мінімум невідсортованого суфікса. Shell робить insertion sort для підпослідовностей із певним gap; halving закінчується на 1. Merge ділить напіввідкритий інтервал `[left,right)` і бере лівий елемент при рівності — саме це забезпечує стабільність. `System.arraycopy` копіює вже злитий результат і не виконує сортування.

Поясни, чому для list lookup починаємо з ближчого кінця, але асимптотика лишається O(n). Чому для merge додатковий масив O(n), а стек O(log n)? Чому `Comparator.reverseOrder()` не вимагає переписувати алгоритм? Чому `Integer.MIN_VALUE - Integer.MAX_VALUE` небезпечно використовувати як компаратор?

Тест із 5 000 операцій порівнює спостережувану поведінку з `ArrayList`, перевіряє прямий/зворотний обхід та інваріанти. Він може виявити втрату вузла, невірний tail чи count. Сортування порівнюється з незалежним бібліотечним еталоном; окремий тест перевіряє identity-порядок однакових ключів.

Практичне завдання перед співбесідою: додай `contains`, власноруч напиши тест видалення середнього елемента, відлагодь merge на `[3,1,2,1]`, поясни випадок `insert(0,x)` у порожній список. Запусти `mvn verify` після зміни. Не називай benchmark JMH чи доказом переваги Java; поясни warm-up, межу timed interval і шум.
